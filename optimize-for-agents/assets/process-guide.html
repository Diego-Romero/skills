Guidance-check proposals ↓
Step 1

Start clean, then audit

Latest remote main→Detached worktree

Save the starting commit. Keep the audit, edits, and checks here; preserve existing checkouts.

Lead agent: establish the overview

Purpose, stack, build/run setup, apps, packages, and their boundaries.

Subagents: investigate in parallel

  • Structure: current tree, instruction files, scopes, pointers, and areas without local guidance.
  • Building blocks: pages, forms, endpoints, UI/styling, database access—where present. Include their testing approach, setup, focused commands, actual variant cases, and gaps.
  • Shared testing & CI: suites, shared setup, workflows, triggers, required-check evidence, existing documentation checks.
  • Terminology: repo-specific meanings, aliases, and conflicting usages.
  • Decisions: existing ADRs and documented choices that could become drafts.
What counts as a useful pattern?

A shared rule, meaningful observed variants, when each applies, a short real code example, and what breaks if ignored.

Endpoint validation, authentication, authorization, and CSRF are separate dimensions. Button styles and interaction states are different dimensions too. Avoid inventing every possible combination.

Preferred for new work needs evidence: shared APIs, active usage, tests, explicit guidance, migration or deprecation notes. The newest file alone is insufficient.

Commands: git fetch, git worktree add --detach, git status, git rev-parse HEAD. Investigations are agent work, not an inventory script. Without subagents, use the same scopes sequentially.

Result → Evidence, uncertainties, and proposals, kept distinct.

Step 2

Prepare drafts, then review

Draft Markdown in repo→At-a-glance proposal→Edit files + discuss

Full pattern, variant, and testing details live in editable repository files. The proposal links to them and summarizes the base, meaningful variants, and existing test cases.

Keep active instructions intact until review; use proposed copies for those changes. A saved report is a snapshot: read back file edits and regenerate the summary.

  1. Structure: one proposed tree with changes marked against the current structure.
  2. Patterns and tests: compact base/variant/test summaries and draft links. Full examples, setup and commands are in the files.
  3. Glossary: suggested definitions and naming discrepancies.
  4. Decisions: existing records and source-backed ADR candidates.

One long page, without tabs: headings, file diffs, reusable component cards, and interactive reading plans. Explanations live here in the side panel. Choose what to keep, change, or drop before implementation. Missing instruction files do not automatically need filling.

Script: proposal-report.mjs presents the findings in this report. This guide is included in the same HTML. DaisyUI CSS loads from a pinned CDN; --offline embeds the bundled styles instead.

Result → Agreed guidance and file layout.

Step 3

Refine the agreed guidance

Short instructions→Direct pointer→Relevant guide

Read back the maintainer’s draft edits. Finalize placement and activate agreed instruction pointers in the original detached worktree. Move before trimming; preserve behavioral guardrails. Keep code behavior unchanged.

Group related variants together. Prefer lint, types, or tests for enforceable rules. Reuse existing glossary and decision records.

Tools: normal editing tools. The separate record-adr skill can draft and review already-made decisions. Do not invent rationale, dates, or acceptance.

Result → Short instructions and evidence-backed guides, including existing testing practices.

Step 4

Check discovery

Verify links, anchors, snippets, and actual instruction loading. Now choose real tasks and walk the routes from the root and relevant subdirectories.

Checks: use relevant repository checks. There is no bundled link checker. Optional run.mjs compares factual questions with fixed model settings at two recorded revisions; it calls eval-report.mjs to build the results page.

Test cards distinguish found/not found/not inspected, and inspected/not executed/executed. Coverage claims need case evidence; a passing suite alone does not establish every variant is covered.

For evals, agree on questions before editing and validate instruction loading and grading on a small control first. Review paid calls and budget before running.

Result → Verified routes and a clear account of what was checked.

How does the reading plan relate to context?

The reading plan is illustrative, not a live trace. Stages show cumulative planned reads; reading test examples is separate from executing tests. Unverified automatic instruction loading stays labelled unknown. Switching components or variants starts a fresh illustration, not a demonstration of forgetting prior context.

Keep common instructions small and read detailed guides when needed. Once read, a guide may remain in later turns. Context is not automatically removed each turn.

Smaller instructions alone do not establish lower total context, fewer turns, or better code. Evals measure factual retrieval and effort on the chosen questions.
